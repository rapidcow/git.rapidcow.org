How to clone

At the moment we support HTTP+SSL protocol on port 443:

git clone https://git.rapidcow.org/pub/...

Or anonymous SSH:

git clone guest@git.rapidcow.org:pub/...

(Git protocol (port 9418) is unsupported at the moment - sorry!)

I have no plan to support raw HTTP; you will be re-directed if you use port 80; sorry. Raw HTTP traffic is too easy for attackers to fake. Good thing that the official Git binaries today usually comes bundled with OpenSSL, so unless you are bringing your own Git client, this shouldn't be an issue.

Those of you who like shortcuts may like to hear that wherever you type "git.rapidcow.org", you can type "git.rdkw.org" instead. They share the same A/AAAA records, and thus point to the same server (in fact, "rapidcow.org" also points to the same server, but don't count on it :x)

As to how you can go about remembering the short name: think of it as taking the first and last letters of "rapid cow", but you spell "c" the way it's pronounced.) But because I have a better reputation as rapidcow.org than as a short domain I came up on a whim this spring, "git.rapidcow.org" will always be the "official" advertisement, while "rdkw.org" will just be a shortcut, for as long as I legally own the domain (and no silly company tries to acquire it or anything. :)

Repository homepage

The homepage for a repository, if one exists at all, would be a very minimal page documenting the purpose of a repository, as well as the locations it is mirrored at. You can usually derive such a homepage page by replacing the ".git" at the end of the HTTPS clone URI with a "/". For example, this clone URI:

git clone https://git.rapidcow.org/pub/school/wisc/sdc/fa-25/team.git

becomes pub/school/wisc/sdc/fa-25/team/

Footnote on infrastructure

Meta-references (refs/info/*) are a distributed and auditable mechanism for changes made to the repository itself. Such an auditing trail for repositories hosted on this server is recorded in refs/info/rdk-self, if one exists (and if one is available for the public to access).

This server employs a basic ACL for repository read/write access. The identity for anonymous shell users is "guest@rapidcow.org", and the identity for anonymous HTTPS users is "www-data@rapidcow.org" (this is not implemented and you may not push over HTTP until I figure out how client certificates work, but this is the plan at least). While neither protocols forbid users to run git-receive-pack at a transport level, repository ACLs are often (if not always) configured to deny anonymous users of the permission to push refs (though it should be clear why such ACLs are in place. :)
